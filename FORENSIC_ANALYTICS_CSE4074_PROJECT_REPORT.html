1. Abstract & Executive Summary

In electronic criminal proceedings and incident response workflows, maintaining unassailable proof of evidence integrity is required for statutory courtroom admissibility. Conventional forensic triage and hashing methods rely on single global digests (e.g., standard SHA-256 or MD5). While such hashes verify overall bitstream equality, they function purely as a binary indicator: an altered hash informs the investigator that a file has been modified, but provides zero information about where, how much, or what specific byte sectors were manipulated. Furthermore, electronic artifacts exhibit extreme structural polymorphism (e.g., JPEG EXIF tags, GPS telemetry, PDF stream dictionaries, Windows PE section tables), which creates severe table sparsity and relational JOIN bottlenecks when forced into traditional SQL schemas.

ForenSight is a full-stack digital forensics and evidence management platform designed to resolve both challenges. It introduces deterministic 4096-byte Merkle tree block slicing to pinpoint the exact physical byte offsets of tampering; an $O(1)$ memory streaming multi-hasher (MD5, SHA-1, SHA-256 with 64 KB buffers); a five-tier diagnostic core (magic byte verification, EXIF/GPS telematics, Error Level Analysis with OpenCV Jet heatmaps, and temporal paradox detection); an append-only SHA-256 hash-chained custody ledger; and a MongoDB document store utilizing compound indexes and explain-plan-optimized queries.

Legal Admissibility Guarantee: The platform complies with ISO/IEC 27037:2012 (Digital Evidence Handling) and automatically compiles certified PDF declarations fulfilling Section 63(4) of the Bharatiya Sakshya Adhiniyam, 2023 (BSA) (superseding Section 65B of the Indian Evidence Act, 1872).

3. Forensic Analytics & Core Algorithms

3.1 Stream-Buffered Multi-Algorithm Hashing ($O(1)$ RAM Complexity)

Loading multi-gigabyte forensic disk images into memory causes fatal Out-of-Memory (OOM) failures. ForenSight executes single-pass chunk streaming using 64 KB memory buffers: 

CHUNK_SIZE = 65536  # 64 KiB buffer
hasher_md5 = hashlib.md5()
hasher_sha1 = hashlib.sha1()
hasher_sha256 = hashlib.sha256()

with open(file_path, "rb") as f:
    while chunk := f.read(CHUNK_SIZE):
        hasher_md5.update(chunk)
        hasher_sha1.update(chunk)
        hasher_sha256.update(chunk)
  • Time Complexity: $O(N)$ where $N$ is total file byte length.
  • Space Complexity: $O(1)$ constant overhead (never exceeds 64 KB RAM).
  • Collision Protection: Guards against MD5/SHA-1 collision attacks by requiring all three digests to match baseline intake values.

3.2 4096-Byte Merkle Tree Slicing & Tamper Localization

The bitstream is sliced into deterministic 4096-byte blocks: $B = \{B_0, B_1, \dots, B_{k-1}\}$. Each leaf digest is computed as $H_i = \text{SHA-256}(B_i)$, followed by pairwise tree reduction: 

                      [ Merkle Root ]
                         /        \
                 [ H_01 ]          [ H_23 ]
                 /      \          /      \
              [ H_0 ]   [ H_1 ]  [ H_2 ]  [ H_3 ]
              (Block0)  (Block1) (Block2) (Block3)
              [4096 B]  [4096 B]  [4096 B]  [4096 B]

Byte-Level Tamper Localization Algorithm:

When verifying candidate evidence against the baseline manifest:

  1. The candidate file is sliced and hashed: $\{H_{\text{cand}, i}\}$.
  2. Differing blocks are isolated: $\text{DiffBlocks} = \{ i \mid H_{\text{cand}, i} \neq H_{\text{ref}, i} \}$.
  3. Each differing block maps directly to physical byte offsets: Offset Range = [i * 4096, (i + 1) * 4096 - 1]
  4. The system renders an interactive Tamper Sector Grid in the UI with false-color OpenCV JET heatmaps.

3.4 Append-Only Hash-Chained Chain of Custody

Every evidence custody transfer is linked using cryptographic parent-child hash chaining: 

Payload_k   = CanonicalJSON(evidenceId, action, fromCustodian, toCustodian, timestamp, reason)
EventHash_k = SHA-256(EventHash_{k-1} || Payload_k)
Where EventHash_0 = SHA-256("00000000000000000000000000000000")

If any database administrator or attacker modifies or deletes a historical handover, recalculating the sequence fails at index $k$, immediately flagging Custody Chain Compromised.

3.5 Continuous 30-Second Integrity Watchdog Daemon

An autonomous asyncio background daemon sweeps all stored evidence every 30 seconds. If an out-of-band disk modification occurs, the daemon detects the hash mismatch, logs an urgent finding, and broadcasts instant alerts via Server-Sent Events (SSE).

4. NoSQL Database Architecture (MongoDB)

ForenSight utilizes MongoDB 7.0 (WiredTiger Storage Engine) across 8 collections: cases, evidence, custodyEvents, analysisJobs, findings, auditLogs, watchdogAudits, and users.

  • Embedding: Merkle blocks and hashes are embedded inside evidence for single-seek disk I/O.
  • Referencing: Evidence references cases (caseId) and custody events reference evidence (evidenceId) to prevent exceeding MongoDB's 16 MB BSON document size boundary.
  • Compound Indexes: idx_case_acq on [("caseId", 1), ("acquisitionTimestamp", -1)] guarantees index-covered retrieval (`IXSCAN`), eliminating in-memory sorting penalties (`SORT` stage).

6. Conclusion

The ForenSight project successfully addresses the core limitations of conventional binary hashing in digital investigations. By combining deterministic 4096-byte Merkle tree block slicing, $O(1)$ memory streaming multi-hashing, a 5-tier diagnostic core, append-only cryptographic custody chaining, and an explain-plan-optimized MongoDB NoSQL database, the platform satisfies all legal admissibility criteria under Section 63(4) of the Bharatiya Sakshya Adhiniyam, 2023 and ISO/IEC 27037:2012.
